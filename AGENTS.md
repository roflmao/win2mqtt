# AGENTS.md

Guidance for AI coding agents (and humans) working in this repository.

## What this project is

win2mqtt is a small Go daemon for Windows desktops, ported from
[mac2mqtt](https://github.com/roflmao/mac2mqtt). It publishes system status
(volume, active app, display, lock state, user activity, network, ...) to an
MQTT broker, accepts commands (volume, mute, sleep, display sleep, lock,
shutdown, reboot) back over MQTT, and announces everything to Home Assistant
via MQTT auto-discovery.

The design is in `docs/superpowers/specs/2026-10-28-win2mqtt-design.md`.

## Layout

| Path | Purpose |
|------|---------|
| `main.go` | Entry point: logging, config, wiring, 2 s / 60 s / hourly tickers |
| `config.go` | YAML config and defaults |
| `system.go` | The `System` interface (everything we need from the OS) and pure helpers |
| `system_stub.go` | `stubSystem`: fixed values; used on non-Windows hosts and as the base for test fakes |
| `system_other.go` | `newSystem()` for non-Windows builds (returns the stub) |
| `system_windows.go` | `newSystem()` for Windows: Win32 queries and commands |
| `audio_windows.go` | Core Audio volume/mute on a dedicated COM thread |
| `window_windows.go` | Hidden window + message loop feeding display-on and screen-locked state |
| `iftable.go` | `MIB_IF_ROW2` layout and the counter summing (untagged so tests can check the layout) |
| `mqtt.go` | MQTT client, dry-run dummy client, `publish`, `warnOnce`, on-connect flow |
| `sensors.go` | One `updateFoo` publisher per sensor, `updateFast`/`updateSlow` groups, network rate maths |
| `commands.go` | Command topic dispatch |
| `discovery.go` | Home Assistant discovery entities |
| `update.go`, `relaunch_*.go` | Self-update from GitHub releases and the Windows relaunch |

| `README.md` | User documentation incl. the metrics and command tables |

## Build and test

Development happens on Linux or macOS; there is usually no Windows machine at hand.

```bash
go vet ./... && go test ./...                      # platform-agnostic core
GOOS=windows go vet ./... && GOOS=windows go test -c -o /dev/null .
GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build -ldflags "-H windowsgui" -o win2mqtt.exe .
```

Run all of these before claiming work is done. `CGO_ENABLED=0` is mandatory;
the Windows layer must stay pure Go (`golang.org/x/sys/windows`, `go-ole`,
`go-wca`, lazy-loaded DLL procs).

To exercise the MQTT flow without Windows, set `dry_run: true` (publishes are
logged) or point a `win2mqtt.yaml` at a real broker: the stub `System`
publishes fixed values and the device appears in Home Assistant. Remove the
retained discovery topics for the Linux hostname afterwards.

## How sensors are structured

1. **System method**: add it to the `System` interface in `system.go`,
   implement it in `system_windows.go` (and keep any parsing or arithmetic in
   a pure helper with a test), and give `stubSystem` a fixed value.
2. **Publisher**: `updateFoo(c)` in `sensors.go` publishes to
   `win2mqtt/HOST/status/foo` via `a.publish`. On error call
   `a.warnOnce("foo", err)` and skip the publish. Never exit.
3. **Schedule**: add it to `updateFast` (cheap, every 2 s) or `updateSlow`
   (every 60 s).
4. **Discovery**: add an entity in `discoveryEntities` with the shared
   availability block. Optional hardware goes behind a `Features` flag so the
   entity is omitted when absent.
5. **Docs and tests**: README metrics row, `sensors_test.go` /
   `discovery_test.go` (entity count changes!), tick TODO.md.

Commands: a `System` method, a case in `handleCommand`, a button in discovery,
a README row, a test in `commands_test.go`.

Keep topic names and payload formats stable once released.

## Rules of the road

- After startup nothing may call `log.Fatal`; sensors and commands log and
  carry on.
- No WMI or PowerShell at runtime. Every OS or broker call made from a
  schedule must be bounded (audio worker timeout, Paho write timeout); the
  fast, slow and update schedules run independently and skip ticks while busy
  (`runOnTicks`), so one slow source never stalls the others.
- Windows-only code lives in `*_windows.go`; everything else must compile and
  be tested on Linux.
- Retained messages on command topics are ignored on purpose.

## Git workflow

- Work on a feature branch, open a PR against `master`, merge with a merge commit.
- **Every push to `master` is a release.** CI bumps the patch version, builds
  a CHANGELOG entry from commit subjects, builds `win2mqtt-windows-amd64.exe`
  and `win2mqtt-windows-arm64.exe`, and publishes a GitHub release that
  installed clients pick up within the hour.
- To release a specific version, tag the commit `vX.Y.Z` before pushing;
  CI then uses that tag, skips the CHANGELOG bump (write the entry yourself),
  and still builds and publishes the release.
- Commit subjects are short, user-facing, imperative sentences.
- No AI co-author or "generated by" attribution in commit messages.
